# Initial release delivery contract

## Identity and retained content

Current product version0.1.0 is authoritative across software/docs/master schema. Existing0.0.0 trees and captured references remain byte-identical. Current-version readers select their matching owned contracts; intentional historical/refusal fixtures retain their meaning. Product persistence schema behavior is not silently broadened.

## Private actual candidate qualification

After native assembly, ci-release qualifies the complete source manifest with latest stillv0.0.0 and the actual accepted native0.1 candidate. Output is .local/release-candidate-site; separate receipt .local/release-candidate-docs.json retains the gated record and exact manifest/output context. CI must retain both. Independent readback rehashes original package/archive inputs, compares assembled candidate identity, recomputes this actual candidate gate and uses the actual headless browser. The canonical .local/release-assembly.json remains the original assembly contract.

Controlled future-version publication fixtures have their own isolated baseline-only source manifest and fixture-qualified records. They exercise recovery and both renderer contexts without claiming actual product publication or electing production downloads.

## Public selection and source capture

Source manifest latest remainsv0.0.0 until the canonical published0.1 record exists. Existing publicSiteInputs derives latest and visible released snapshots from actual service records. Fully authored docs/schema source is committed before its capture receipt cites that real source revision. If a never-published pending snapshot changes after review, verify publication absence and recapture only its receipt through disposable output; do not change a published snapshot or invent a historical correction event.

## Owner merge and publication

PR phase closes #20/#21 decisions but only references #74. Stop at final owner review and squash merge. After that merge, acquire a successful push-to-main Qualification run containing version0.1.0, all elected terminal receipts and original native archives. Independently read them back, then dispatch existing release.yml on main with elected version0.1.0, empty previous_version, accepted qualification_run and concise highlights. Product release execution revalidates both actual docs contexts and unchanged native inputs before canonical/latest promotion. Pages deploys the separately accepted export without rebuilding.

Completion requires actual tag/source identity, six primary artifacts plus supporting metadata, canonical release.json, independent hash/size/URL readback, latest/docs/download correspondence and successful exact Pages deployment. No signing/notarization/stapling, no extra attended pre-release gate and no workstation-focus qualification is introduced.
